02

Zendesk + Sentry Integration

Early issue detection

Catches issues early from customer complaints: each helpdesk ticket is linked to the customer's click trail and production errors, then classified as a real bug or not, so problems surface before they spread. Fully read-only.

3data sources
4Sentry outcomes
3-tierclassification
Hours → mincomplaint verification time

Value

  • Faster, verified feedback loopVerifying a complaint used to take a few hours; now it takes a few minutes, because every ticket is already checked automatically and flagged. The automatic Zendesk ↔ Sentry cross-check tells QA whether a complaint is a real technical problem: a clear valid issue or not an issue, not just “there is a report”. Real issues go straight to follow-up.
  • Healthier customer sentimentThe sooner a bug is confirmed, the sooner the customer gets a clear answer and the fix is scheduled. When it is not a technical issue, that is known early too, so no effort is wasted on needless investigation. Both improve the customer experience and team efficiency.

Features

  • Ticket → customer ID → customer journey → Sentry error search
  • Sentry outcome: strong match, weak match, no error, or search failed
  • 3-tier classification: manual override → rule-based → AI
  • Confirmed bugs pushed automatically to the QA Slack channel
Zendesk APISentry APILLM classificationRoot cause analysis

Workflow · Investigation path

  1. TicketFetch the ticket through the helpdesk REST API, read-only; take the customer ID from the message.
  2. FallbackNo customer ID? Look it up from the booking code in the order system.
  3. JourneyOpen the customer-journey dashboard for that ID and check the date range.
  4. CompareCompare the click-by-click journey with what the customer reported.
  5. SentrySearch by booking code, then customer ID: strong match, weak match, no error or search failed.
  6. AnswerTimeline, Sentry result and conclusion; confirmed bugs go to the QA Slack channel.

Workflow

How a ticket gets tested

The flow the team follows for every ticket, from intake to close. AI runs the repetitive steps; the QA team keeps the final call.

  1. IntakeTicket picked from the QA filter after two gates: not yet tested, code review approved.
  2. ReadAn AI agent reads the ticket and its acceptance criteria.
  3. EnvironmentTest environment set up per platform: desktop, mobile web, Android or iOS.
  4. ExecuteDeveloper test cases run, with evidence captured for each one.
  5. ReportA structured QA result posted to Jira: PASS, FAIL, NEED MANUAL or NO TASK.
  6. CatalogNew cases converted and appended to the test case knowledge base.
  7. ReviewThe QA team reviews every AI result.
  8. CloseThe QA team sets the final Jira status.
