01

QA Command Center

One dashboard for the whole QA team: daily E2E results, the test case catalog, app pre-release, complaint triage, team performance and quarterly reports. Refreshes automatically every 10 minutes.

  • E2E run matrix by day × scenario, with error and skip-reason popups
  • Full-text search across every test case with a built-in viewer
  • Q1–Q4 reports: incidents, improvements, team and test case growth
  • Shared login (HMAC cookie, rate-limited), public build that strips internal fields
  • Encrypted AES-256 daily backup to two locations
  • 18 Playwright smoke checks + 25 unit tests on every change
PythonHTTP serverJira APISentry APIPlaywrightSVG charts
Workflow

How it runs

  1. ScanGenerator scans the test case knowledge base and both automation repos.
  2. PullFetches Jira, Sentry and helpdesk data over REST APIs; finished months come from a cache.
  3. ClassifyTags helpdesk tickets in 3 tiers: manual override → fixed rules → AI.
  4. RenderBuilds the dashboard HTML plus a public build with internal fields stripped.
  5. ServeServed to the team with a shared login at http://brandname:8787; refreshes every 10 min, daily snapshot at 20:00.
  6. Verify18 Playwright smoke checks and 25 unit tests after every change; encrypted backup nightly.
02

Test Case Management

A Markdown-based test case management system designed to be read by people and AI alike: 4,000+ cases in 40+ feature files, one index, and consistent IDs.

  • One file per feature with a Case ID prefix (for example PAY, AUTH, FR)
  • Separate folders for E2E scenarios, pre-release regression and incidents
  • Jira tickets converted automatically into test cases in a standard format
  • Catalog consistency audits that catch miscategorised cases
  • Scenario files double as configuration for the automation suites
Test designMarkdownGitInformation architecture
Workflow

From ticket to catalog

  1. CategoriseRead the Jira ticket and pick the one catalog file that matches its content.
  2. De-duplicateSearch the Jira key across the catalog; existing cases are updated, never duplicated.
  3. AppendAdd cases with the next Case ID from the file prefix, e.g. PAY-0xx.
  4. Tag platformTag (APP), (MOBILE WEB) or (DESKTOP) only when the ticket scopes a platform.
  5. RegisterA new category gets its own file and prefix in the index; counts are never stored by hand.
  6. AuditPeriodic consistency audit finds stray or miscategorised cases.
03

AI QA Agents

35+ agent skills that let AI test Jira tickets on its own: read the ticket, pick the platform, run the tests, collect evidence, and post a structured QA result.

  • Platform detection from ticket components: desktop, mobile web, Android or iOS
  • Strict verdicts: PASS, FAIL, NEED MANUAL or NO TASK, never partial
  • Evidence rules: SSR, timing and metric claims proven with text evidence, not screenshots
  • Per-ticket call budget to keep AI cost under control
  • Separate skills for incidents, weekly reports and daily Sentry triage
LLM agentsModel Context ProtocolJira REST APIPrompt engineering
Workflow

Ticket loop

  1. PullTake the next ticket from the Jira QA filter.
  2. Gate 1Skip if the bot already posted a QA Result.
  3. Gate 2Continue only when the CR-APPROVED label is set.
  4. ReadRead the ticket and AC; detect platform from Components (Web = desktop + mobile).
  5. ExecuteRun every developer test case and capture evidence.
  6. VerdictPASS, FAIL, NEED MANUAL or NO TASK, never partial.
  7. PostFormat gate on the comment, then post the QA Result to Jira.
  8. CatalogConvert and append the cases to the test case catalog.
  9. Human reviewQA team checks the bot’s steps and sets the final status.

Workflow

Flight booking scenario

  1. SearchOpen new.brandname.com/en/flight; set trip type, passengers, cabin, route CGK → DPS and date.
  2. SelectFilter by airline, pick the first result and a fare; record the price.
  3. BookFill passenger and contact details, add the smallest paid baggage, confirm.
  4. Add-onsDecline travel protection; skip seats and meals.
  5. PayRecord the booking code, pay with a test card and pass 3DS OTP.
  6. VerifyOrder shows Payment Success; product, dates, passengers and price match what was recorded.
05

Customer Complaint Triage

A pipeline that links each helpdesk ticket to the customer's click trail and production errors, then classifies whether it is a real bug. Fully read-only.

  • Ticket → customer ID → customer journey → Sentry error search
  • Sentry outcome: strong match, weak match, no error, or search failed
  • 3-tier classification: manual override → deterministic rules → AI
  • Confirmed bugs pushed automatically to the QA Slack channel
Zendesk APISentry APILLM classificationRoot cause analysis
Workflow

Investigation path

  1. TicketFetch the ticket through the helpdesk REST API, read-only; take the customer ID from the message.
  2. FallbackNo ID? Booking code → order record on book.brandname.com, or search the CS portal by email or name.
  3. JourneyOpen the customer-journey dashboard for that ID and check the date range.
  4. CompareRead the click-by-click journey against what the customer reported.
  5. SentrySearch by booking code, then customer ID: strong match, weak match, no error or failed.
  6. AnswerTimeline, Sentry result and conclusion; confirmed bugs go to the QA Slack channel.

The Android and iOS release sign-off process I designed: an SOP, a structured regression checklist, and a pre-release log in the dashboard.

  • Checklist run separately for mobile web and the native app
  • Low-end (2–4GB RAM, older OS) and high-end (flagship, latest OS) device coverage
  • Automation on emulators for core flows, manual for new features
  • Payment tested twice, card and non-card, plus vouchers and currency change
  • Log of new builds, builds needing testing, and sign-off history

Workflow

How a ticket gets tested

The flow the team follows for every ticket, from intake to close. AI runs the repetitive steps; the QA team keeps the final call.

  1. IntakeTicket picked from the QA filter after two gates: not yet tested, code review approved.
  2. ReadAn AI agent reads the ticket and its acceptance criteria.
  3. EnvironmentTest environment set up per platform: desktop, mobile web, Android or iOS.
  4. ExecuteDeveloper test cases run, with evidence captured for each one.
  5. ReportA structured QA result posted to Jira: PASS, FAIL, NEED MANUAL or NO TASK.
  6. CatalogNew cases converted and appended to the test case knowledge base.
  7. ReviewThe QA team reviews every AI result.
  8. CloseThe QA team sets the final Jira status.
